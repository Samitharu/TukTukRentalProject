# Phase 5 Summary — Public Website, Design System, Booking Flow

Status: **core deliverables complete and live-tested end-to-end**; two items are explicitly deferred (see "What's deliberately not in this phase" below), continuing under the "continue all remaining phases" authorization rather than pausing for confirmation.

## What was built this phase

### Design system
Hand-written, no build step (brief §2): `public/assets/css/tokens.css` (design tokens — fluid type via `clamp()`, tropical-professional palette, dark-mode media-query support) and `public/assets/css/public.css` (mobile-first components: header/nav, buttons, cards, hero, forms, footer, WhatsApp float button, sticky mobile "Book Now" bar, cookie-consent banner, steps indicator, price-breakdown component). Alpine.js core vendored as a single self-hosted minified file (no plugins) — `x-collapse` was never used; the FAQ accordion and mobile nav use plain `x-show`/`x-cloak` instead, and `[x-cloak] { display: none !important; }` was added to `public.css` for it to work at all.

### Locale-aware public routing
`Modules\Localization\Http\Middleware\SetLocale` now calls `URL::defaults(['locale' => $code])`, so every public route shares one name across all four languages (`route('fleet.show', $slug)`, not `route('en.fleet.show', ...)`) — the `{locale}` segment fills in automatically. `Modules\Localization\Support\HasTranslatableSlug` (new trait) gives Fleet's `Vehicle`, Package's `Package`, and CMS's `Page`/`BlogPost` per-locale slugs synced on save, with collision-safe suffixing. `LocaleRouteRegistrar` gained a `LOAD_LAST` mechanism so CMS's catch-all `/{slug}` page route always loads after every other module's more specific routes — it would otherwise alphabetically shadow `/tuk-tuks`, `/packages`, etc.

### CMS module (new)
Pages, FAQs (accordion, grouped by category), testimonials, a blog, reviews (moderation only — no public submission), and a contact form with a honeypot field (`prohibited` validation rule) for spam resistance. Rich text is sanitized server-side via `mews/purifier` on every save (a `cms_content` preset was added to `config/purifier.php` specifically) — caught and fixed before it ever rendered: the first draft read the model's translatable attribute through its magic accessor, which only returns the *current* locale's string, and would have silently dropped every other language's content on save. Fixed using explicit `getTranslations()`/`setTranslations()`. Seeded with real content (About Us, How It Works, a Driving Permit guide, 5 FAQs, 3 testimonials), not placeholder text — Terms/Privacy/Cancellation are the one exception, left as `[Placeholder — confirm with...]` exactly where the business brief itself supplied no real policy.

### Homepage, Fleet, Packages, Pricing (new)
Real controllers and views replaced the Phase 2 "coming soon" placeholder. A new **Pricing page** (`Modules\Package\Http\Controllers\Front\PackageController::pricing()`, route `pricing`) lists every active package's full tier table in one place — the brief lists this as a distinct public page separate from the package detail pages.

### The public booking flow (this phase's centerpiece)
A server-side, session-backed 5-step wizard (`Modules\Booking\Support\BookingFlowState` + `Modules\Booking\Http\Controllers\Front\BookingFlowController`) — not a client-side SPA, matching the rest of the site's no-build-step constraint:

1. **Dates** — pickup/return dates, pickup method (office pickup vs. delivery, with the relevant location/zone picker).
2. **Package** — filtered to packages whose `min_days`/`max_days` actually cover the selected range; a tuk tuk pre-selected from its own Fleet page (`?vehicle=`) carries through if it's eligible for the chosen package, otherwise it's dropped and `BookingService` auto-assigns.
3. **Add-ons** — package-included add-ons are shown as already-included (not selectable — see "bug found" below); selectable ones get a quantity stepper; an optional coupon code field.
4. **Driver details** — name, email, phone, nationality (an ISO 3166-1 alpha-2 `<select>`, backed by a new `Modules\Core\Support\Countries` reference list — free text was rejected during review since `customers.nationality` is a `char(2)` column and would have thrown on anything else), passport number, licence/IDP status, special requests.
5. **Review** — a live price breakdown with the brief's explicitly-required AJAX recalculation (`POST booking/review/recalculate`, JSON), used for applying a coupon without a page reload. Every total is recomputed server-side from scratch here and again at confirm — nothing the client sent is ever trusted as a total (brief §7).

Since online payment stays disabled (confirmed decision, Phase 1), `confirm()` calls `BookingService::createHold()` immediately followed by `confirmHold()` in the same request — no lingering hold, no separate payment step — identical to the pattern `createManualBooking()` already used for admin walk-ins. The booking goes straight to `confirmed`. A non-sequential `MTR-XXXXXXXX` reference is shown on a confirmation page (`booking/confirmation/{reference}`) that deliberately never displays the passport number.

### Two real bugs fixed along the way (not introduced, but shipped-and-caught here)
1. **Coupon `usage_count` was never incremented anywhere** — `Coupon::isValidFor()`'s own docblock said "that only happens once a booking is actually confirmed," but Phase 4's `BookingService::confirmHold()` never did it. A coupon with a `usage_limit` could be redeemed unlimited times. Fixed by incrementing inside the same transaction, keyed off the confirmed `PriceBreakdown`'s `couponCode` — verified live: a coupon's `usage_count` went from 0 to 1 on confirm, and stayed at 1 on a second (idempotent, same-hold) confirm attempt.
2. **Driver-collected data (IDP status, special requests) had nowhere to be stored.** The booking flow's step 4 explicitly collects this per brief §4, but `bookings` had no columns for it. Added via migration (`has_international_permit`, `special_requests`) rather than silently discarding what the customer typed — also threaded through the admin manual-booking form and booking detail view for parity between both booking channels (brief §6 point 8: admin uses the same service, so it should be able to record the same data).

### A bug this session introduced and caught before it shipped
The new `resources/views/errors/*.blade.php` pages were built to look right, but the 404 page initially used the full public site layout (`x-core::layouts.public`), which calls `route('fleet.index')` etc. Those need a `locale` URL default that only `SetLocale` sets — and `SetLocale` never runs for a request that fails to match *any* route (an inactive-locale prefix like `/fr` when `fr` isn't seeded active, or a totally unrelated path). That turned a 404 into a secondary 500 during the error page's own rendering, caught by the existing `LocaleRoutingTest`'s "does not offer an inactive locale as a route prefix" test going from pass to fail. Fixed by making 404/419/429/500/503 fully self-contained (inline CSS, no named-route calls, no DB). A second, subtler bug surfaced while fixing the first: the shared partial was named `minimal.blade.php`, which collided with Laravel's *own* built-in `errors::minimal` layout (used internally by its default 401/402/403/419/429 templates) — app view paths take priority over the framework's fallback path in the same namespace, so this silently broke the framework's default 403 page everywhere in the app until it was renamed to `_layout.blade.php`. Both are now covered by `Modules\Core\tests\Feature\ErrorPagesTest`.

### Critical post-delivery fix: Alpine never actually worked, anywhere, all phase — CSP was silently blocking it

After the above was first marked complete, real user reports (a cookie-consent "Got it" button and a language dropdown that visually appeared but didn't respond to clicks) led to driving the live site with an actual browser (Playwright against the system's installed Edge, launched ad hoc for this one investigation — not a project dependency) instead of `curl`, since `curl` can execute HTTP requests but never JavaScript and so had been silently validating markup, not behaviour. The browser's console told the real story immediately: **regular Alpine.js requires `script-src 'unsafe-eval'` to evaluate any `x-data`/`x-show`/`@click` expression at all** (its evaluator is built on `new Function(...)`), and this project's CSP (`Modules\Core\Http\Middleware\SecurityHeaders`) has never granted that. Every Alpine-driven interaction on the entire public site — the mobile nav toggle, the FAQ accordion, the booking dates step's pickup-type toggle, and both of the user-reported widgets — had been silently non-functional since the moment CSP headers were added, with no error visible to anyone testing via `curl` or by reading the rendered HTML, only via a real browser's devtools console.

Fixed properly rather than by weakening security: `public/assets/vendor/alpine.min.js` is now the official **`@alpinejs/csp`** build (same v3.17.4 release, different distribution), which evaluates directive expressions through its own restricted-grammar interpreter instead of `new Function`, needing no `unsafe-eval` at all. `script-src` stays exactly as strict as before. One further compatibility issue surfaced by the same investigation: that build's grammar doesn't support arbitrary global calls like `JSON.parse(...)` inside an `x-data=""` attribute, which broke the booking review page's price-recalculation component specifically (`x-data="bookingReview(JSON.parse('...'))"`). Fixed by switching to Alpine's documented pattern for this exact situation: `Alpine.data('bookingReview', () => ({...}))` registered in a real `<script>` (plain JS, no expression-grammar limits), with the component reading its initial price/coupon/URL data from `data-*` attributes (HTML-escaped by Blade's `{{ }}`, parsed with a normal in-script `JSON.parse`) inside an `init()` hook, rather than passing anything but a bare `bookingReview()` call through the attribute itself.

A second, independent CSP bug was found by the same investigation: `style-src 'self' 'nonce-{nonce}'` has no mechanism to allow inline `style=""` HTML *attributes* at all (CSP's nonce/hash mechanism only ever covers `<style>` *elements*) — and this project's views use inline style attributes extensively (196 occurrences across 50 files) for one-off layout tweaks. Every one of them was being silently dropped by any CSP-respecting browser. Fixed by adding `'unsafe-inline'` to `style-src` alone — which, per CSP semantics (confirmed empirically, since the spec note is easy to misread), only takes effect once the nonce is *removed* from that same directive, since a nonce-source present anywhere in a directive makes a compliant browser ignore `'unsafe-inline'` for the whole directive. `script-src` is unaffected and keeps its nonce.

All of this was then re-verified with the same real-browser harness: zero CSP console errors or `pageerror` events across the homepage, pricing page, FAQ page, and the full five-step booking flow (including the price-recalculation coupon call and a real confirmed booking), on top of the full Pest suite staying green throughout.

## Live verification performed

Beyond the automated suite (105 Pest tests passing), the full booking flow was driven end-to-end twice: once via real HTTP requests against the dev server and live MySQL database (cookie-jar `curl`), and a second time via an actual browser (see above) specifically because the first method cannot observe JavaScript behaviour at all. Both covered: all 5 steps in sequence, a coupon applied through the JSON recalculation endpoint (and confirmed to visibly update the displayed total, not just the underlying API response), a successful confirmation with a real `MTR-` reference, database rows inspected directly to confirm the customer/booking/addon/coupon-usage data landed correctly, session state confirmed cleared post-confirmation, and every guard path exercised (deep-linking into a later step with no prior state, an invalid coupon code, a day-range outside a package's min/max, a nonexistent confirmation reference). All test data created during manual verification was removed from the dev database afterward.

## Post-phase feature addition: admin-uploadable images

Prompted directly by feedback on the live site (a visual reference image was shared and the question "admin should have option to upload images" was asked). Two gaps were real and worth closing rather than deferring to Phase 7's Settings module:

- **Package photos** — packages had no image support at all, unlike vehicles (`VehicleImage`/`VehicleImageService` since Phase 3). Added `PackageImage` + `PackageImageService`, deliberately mirroring the vehicle pattern exactly (same GD-driver resize-to-WebP-plus-thumbnail approach, same admin upload/gallery/delete UI) rather than inventing a second convention for the same problem. Shows on the package listing, package detail page, the homepage's featured-packages section, and the booking flow's package-selection step.
- **Site branding (logo, homepage hero image)** — previously hand-coded CSS/text only. Added a single-row `site_settings` table (`Modules\Core\Models\SiteSetting`, cached, invalidated on save — same pattern as `Locale::activeCached()`), a `SiteBrandingService` (same resize approach, but replaces-and-deletes the old file instead of adding to a gallery), and one admin screen (`/control-panel/branding`, gated behind a new `settings.manage` permission). The homepage hero becomes a two-column layout with the uploaded photo on the right only once one is uploaded; with nothing uploaded it falls back to the original single-column gradient hero, so this is additive, not a breaking redesign.
- While styling the hero to match the shared reference image's direction, also added four real inline-SVG trust badges (shield/headset/people/calendar, in solid colour circles) under the hero text, and an SVG tuk-tuk icon as the header's logo mark when no custom logo is uploaded. The reference image's more bespoke elements (a custom illustrated logo, hand-drawn script annotations, a photo-collage composition) were explicitly not attempted — those are graphic-design assets, not something CSS should fake, and said so directly rather than quietly approximating them badly.

Verified live (Playwright against the system's Edge): logged in as a non-2FA-enforced role, uploaded a logo and a hero image, confirmed both render correctly on the public homepage with zero console errors, confirmed re-uploading a logo deletes the old file, uploaded a package photo and confirmed it appears in the admin gallery, the public package listing, and the homepage featured section. All test uploads and the test account were removed afterward. 8 new Pest tests cover the permission gates, the upload/replace/remove lifecycle, and the fallback-when-nothing-uploaded behaviour — full suite: 113 passing.
