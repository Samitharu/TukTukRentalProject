# Module List & Justification

`nwidart/laravel-modules` module per row. Order = build order in the phase plan, which is also the dependency order (a module only depends on modules above it).

| # | Module | Responsibility | Depends on | Why it's a separate module (not folded into another) |
|---|---|---|---|---|
| 1 | **Core** | Base model/controller classes, traits (`HasTranslatableSlug`, `HasUuidReference`), middleware (security headers, locale), Blade layout + shared components, response macros, the `asset_v()` helper, `assets:minify` command | — | Every other module depends on it; keeping it separate prevents circular deps and gives one place to enforce coding standards (Pint base config lives here too) |
| 2 | **Localization** | `locales` table + admin CRUD, language switcher, `route_slugs` resolution, missing-translation tracking/dashboard widget | Core | Routing and translated-slug resolution is infrastructure every other customer-facing module consumes; isolating it is what lets new languages be added with zero code changes elsewhere |
| 3 | **Fleet** | Vehicles, categories, images, maintenance logs | Core, Localization | Vehicle data is owned independently of pricing/booking — Availability and Booking *read* Fleet, they don't own vehicle attributes |
| 4 | **Package** | Admin-built rental packages, pricing tiers, seasons, add-ons, package↔vehicle/category links | Core, Localization, Fleet | Pricing composition rules (tiers, seasons, add-ons) are complex enough to warrant their own migrations/services separate from Fleet, and are edited by Content Editors, not Fleet managers |
| 5 | **Pricing** | Coupons, currencies, exchange rates, the price-breakdown calculator used by both the public site and the admin | Core, Package | Price calculation is called from Booking, Package preview, and public JSON endpoints — centralizing it avoids three copies of the same math (and the brief's "never trust client totals" rule needs one authoritative calculator) |
| 6 | **Availability** | Blackouts, buffer/notice/advance-window rules, `vehicle_reservation_slots`, the calendar read API | Core, Fleet | This is the **query side** of the conflict-prevention system; kept separate from Booking so the same availability truth can be queried by the public site (read-only, cached-safe) without pulling in booking-write logic |
| 7 | **Booking** | Holds, bookings, status state machine, conflict-safe reservation writes, invoices | Core, Localization, Fleet, Package, Pricing, Availability, Customer | The highest-risk module (§6 of the brief); isolating it means the "zero double-booking" guarantee has one, auditable, well-tested surface (`BookingService`) rather than being reimplemented per caller |
| 8 | **Customer** | Customer accounts, document upload/verification, booking history | Core | Customers can exist (guest checkout) before a Booking does, and are read by Report/Notification independently of Booking |
| 9 | **Payment** | Gateway interface, deposits, webhooks, refunds | Core, Booking | Payment providers change independently of booking logic; the interface boundary is what makes "add a payment gateway" a Payment-module-only change per the README requirement |
| 10 | **CMS** | Pages, FAQs, testimonials, blog, home sections | Core, Localization, SEO | Content editors need a module whose migrations/permissions don't intersect with Fleet/Booking, so a Content Editor role can be scoped to exactly this module |
| 11 | **SEO** | Meta manager (polymorphic), sitemap, JSON-LD, redirects | Core, Localization | Meta/schema data attaches polymorphically to records in *every* other module — it has to be its own module so it doesn't create a dependency cycle (Fleet doesn't need to know about SEO internals, it just gets a `HasSeoMeta` trait from here) |
| 12 | **Notification** | Queued transactional emails, admin alerts, WhatsApp click-to-chat helper | Core, Customer, Booking | Every module fires events; Notification only listens. Keeping all `Mailable`/`Notification` classes and their 4-language Blade templates in one module keeps translation review in one place |
| 13 | **Admin** | Dashboard, users/roles, settings, system tools (cache/sessions/security/DB/queue/logs/backup/maintenance-mode) | Core, all others (read-only, for dashboard widgets) | The only module allowed to aggregate read access across all others (for the dashboard); it owns no domain data itself, only `users`, `settings`, and operational tables (`login_attempts`, `blocked_ips`) |
| 14 | **Report** | Revenue/occupancy/nationality/language reports, CSV/PDF export | Core, Booking, Customer, Fleet | Reporting queries are read-heavy and report-specific (pre-aggregated where needed); isolating them keeps ad-hoc reporting code out of the transactional Booking module |

### Why `nwidart/laravel-modules` at all (vs. plain `app/`)

Justification (per the "only well-maintained packages, justify each" rule — detailed per-package in [05-packages.md](05-packages.md)): the brief explicitly requires it, and it earns its place independent of that: with 14 bounded contexts, a flat `app/` tree would mix Fleet, Booking, and Admin concerns in the same directories, making the "Content Editor role can only touch CMS" requirement (§5 roles) and the "each module has its own tests/lang/migrations" requirement (§2) much harder to enforce by convention alone. Module boundaries are enforced by directory structure, not just discipline.
